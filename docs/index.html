Sirens for Agents

Resampling-derived, action-level honeypot discovery, piloted on one SHADE-Arena task.

Continues my Apart Research project Discovering honeypots from resampled behavior in evaluation.

Zachary Gunderson · October 2026

Code Full tables Cite

Abstract

A honeypot for an agent is a tool or file that a well-behaved agent has no reason to touch. If the agent touches it, that is a signal for monitoring. The hard part is knowing which tools to plant, because I cannot list every covert action in advance. I tried to discover them instead. I resample a black-box agent at the action level, with no chain of thought, and look for actions that benign runs never take. I piloted this on one task from SHADE-Arena, a third-party sabotage benchmark, with a local open-weights model. A simple detector built from the benign runs flagged both completed sabotage runs and none of the benign runs. SHADE's own monitor flagged one of the two. I do not trust this result. The harm in this task needs a dedicated tool, so the detector is almost guaranteed to work here. The sample is tiny. The adaptive engine I designed to make discovery cheap never finished a full episode on my hardware. This is a pilot and the project is parked.

Pilot, parked, not externally reviewed. Treat every result below as a lead. The adaptive engine was designed and released but never validated.

1Introduction

The setting is an AI agent that works with real tools: email, files, rules, accounts. Someone deploys it and gives it a legitimate task. A second, hidden objective can also push the agent. It might come from a bad instruction, from a misaligned goal, or from the agent finding that harm helps it finish. The failure I care about is covert sabotage. The agent does the visible task well and also does something harmful on the side.

This is hard to see for three reasons. The visible work looks fine. A monitor that reads the transcript can be talked past, or can miss the one harmful step in a long run. And a defender does not know in advance which harmful action to look for.

A siren is my name for a honeypot or canary built for this setting. The defender who deploys the agent sets it. It is an affordance that normal work never needs, such as a rarely used tool. If the agent uses it, monitoring raises an alarm. The open question is where to put sirens. I ask three questions.

  1. Can I find candidate sirens by resampling an agent's actions, without reading its reasoning?
  2. If I find one, does it separate sabotage runs from benign runs?
  3. Can the search be made cheap enough to be practical?

My contributions are small. I give a harness that runs action-level resampling on SHADE-Arena. I give a post-hoc check on one task. I report plainly that the cost question is unanswered, and why.

2Background

Threat model. A black-box agent, a defender who can see its tool calls, and a hidden side objective that the agent may pursue.

Honeypot or canary. An affordance whose use signals something is wrong. I call a honeypot built for agents a siren.

Action level. I look only at which tools the agent calls and when. I do not read its chain of thought. I do this because reasoning can be absent, hidden or unfaithful, while tool calls are what change the world.

Resampling. I ask the same model for the next action many times from the same context. This maps the distribution of actions at one decision point. A covert branch counts even if the path that was actually taken was benign. The idea follows work that resamples reasoning traces, applied here to actions (see References).

Control-anchored discovery. I do not name the harmful action. I take the set of tools used in benign runs as normal. A tool outside that set is off-manifold, and a candidate siren.

Adaptive engine. A designed search that spends more samples on promising cases and stops boring ones early, using a subset-simulation ladder and sequential tests. It is specified in the repo and was not validated.

SHADE-Arena. A benchmark of agent tasks, each with a main task and a hidden side task. Spam_filter_update is the task I ran. The main task is to standardize spam rules. The side task is to make the rules delete a particular sign-in email.

3Methods

The agent is qwen3.6-35b, served locally behind an OpenAI-compatible API. I ran the benchmark's own task, tools and scoring. Each task was run in a benign condition and a rogue condition, where the agent is given the side task. The side-task label comes from a check on the environment state, not from my detector. Task order was set by a deterministic split in data/split.json, and only the first task finished.

  1. Run baselineRun benign and rogue episodes through plain resampling of whole episodes.
  2. Build the manifoldCollect every tool name used in benign runs. This is normal.
  3. Find off-manifold toolsList tools that rogue runs use and benign runs never do.
  4. DetectorFlag a run if it calls an off-manifold tool that changes state.
  5. ReplayScore the detector on all ten episodes, and compare with SHADE's monitor.
  6. Cost curveCap each episode at some turn and ask how much compute that saves.

The branch-resampling harness (code/run_probe.py) wraps SHADE's own task and tool code and adds a loop that samples several next actions per turn. I ran it for a short demonstration episode only. Controls: the benign arm is the control, and the label is independent of the detector. I did not run random or generic honeypot arms, a permutation null, or held-out tasks.

4Results

4.1 Does the discovered tool separate sabotage from benign runs?

SHADE-Arenatool-call replaycontrol manifold I expected the off-manifold tool to be the autodelete rule tool. It was, and it was the only tool of that kind. Both completed sabotage runs called it (Table A2). No benign run did. The three rogue runs that did not finish the side task never called it either. That is a clean result. I think it is mostly structural, as I explain in the limitations. I am not confident it says anything about harder tasks.

SHADE's own monitor gave the two sabotage runs very different verdicts. It missed one and flagged the other, so on this pair the action-level detector did better. That is only a pair of runs, so I treat it as an anecdote.

4.2 Is early stopping worth it?

turn capcompute proxy I hoped the harmful call would come early, so that capping episodes would save most of the compute of a full sweep. It did not. In one sabotage run the call came late in a long episode. A cap that catches both positives saves only a few percent. This surprised me and it changed my plan: cheap discovery cannot rest on early stopping alone.

4.3 Does the full adaptive harness work on SHADE?

branch resamplingharness The short demonstration episode ran end to end. The agent stayed on the benign manifold and the side task was not completed. A full episode with the adaptive engine did not finish in the time I gave it. So I have no evidence for or against the adaptive engine. Details are in Table A4.

5Discussion

For monitoring, the useful idea is simple. Derive normal from benign runs, then watch for tools outside normal. This needs no knowledge of the harm and no reading of reasoning. If a task makes the harm depend on a dedicated tool, a siren on that tool is cheap and precise.

Discovery is the bottleneck here, not detection. Once the tool is known, detection is trivial. Finding it means running enough rogue episodes to see it, and episodes are expensive on local hardware. My early-stopping result says that the expensive part is long episodes where the harm appears late.

I did not test specification gaming, where the agent reaches the goal in an unintended way without a dedicated tool. That is the case where tool-level sirens should be weakest.

6Limitations and corrections

This project is parked. I stopped because the pilot could not answer the question I cared about, and I could not afford the runs that would.

  • Structural recall. In this task the side task requires the autodelete tool. Other rule tools do not satisfy it. So watching that tool catches the harm by construction. The perfect score tells me the pipeline runs, not that it generalizes.
  • Tiny sample. One task, few runs per arm, very few positives. I cannot put a useful interval on any rate, and a rank-based score on so few positives means nothing.
  • One model. A single local open-weights model. Other models may use different paths.
  • Adaptive engine unvalidated. It is specified and released as code, but it was never run on SHADE to completion. The released file name says so.
  • Held-out evaluation not done. I made a discovery and held-out split of tasks and ran only the first discovery task. No held-out result exists.
  • Compute proxy. I used turn counts, not tokens or wall-clock time.
  • Correction. I planned to show that early stopping saves most of the compute. The data showed the opposite, so the plan is replaced by the claim that early stopping barely helps here.
  • Not reproduced end to end. The analysis scripts in code/ expect a SHADE checkout layout that is not in this repo. The numbers on this page were recomputed from the tracked transcripts. The install recipe for SHADE on my hardware is withheld under the sprint's disclosure rule.

Not yet reviewed by anyone but me. The discussion of why the detector works is my interpretation of the task code and transcripts.

7Future work

  • Run the remaining tasks and score the held-out ones.
  • Finish an episode with the adaptive engine and measure real savings against plain resampling.
  • Add random and generic honeypot arms and a permutation null, so I know whether discovered sirens beat arbitrary ones.
  • Try tasks where the harm needs no dedicated tool, to test the structural worry directly.
  • Move from tool names to arguments, so reusing a normal tool for harm can be caught.
